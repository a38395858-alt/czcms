# 自用多语言 CMS：Go、Chi、SQLite 与缓存架构方案

> 文档版本：V2.1  
> 更新日期：2026-08-26  
> 文档状态：正式技术基线  
> 核心目标：轻量、快速、安全、原生 HTML、低服务器成本、可渐进扩展

---

## 1. 最终选型

第一版正式采用：

```text
Go 稳定版
+ Chi（兼容 net/http 的轻量路由）
+ Go html/template（服务端原生 HTML）
+ 原生 HTML / CSS / JavaScript
+ SQLite（WAL）
+ Go 进程内存缓存（L1）
+ Redis 可选共享缓存（L2）
+ SQLite 持久化任务表 + Go 有界 Worker Pool
+ 本地媒体存储起步 / S3 兼容接口扩展
+ 静态 HTML + CDN
```

项目不做前后端分离。公开前台和中文后台均由 Go 服务端直接输出 HTML；JavaScript 只增强交互，不负责公开页面的核心内容与 SEO 数据。

---

## 2. Go Web 框架对比

| 方案 | 优点 | 主要代价 | 本项目结论 |
|---|---|---|---|
| `net/http` | 标准库、最轻、生命周期长、生态兼容最好 | 路由分组、中间件组合需自行组织 | 可直接使用，但第一版选择 Chi 减少重复代码 |
| **Chi** | 很薄、兼容 `net/http`、中间件成熟、易测试、无框架锁定 | 不提供 ORM、模板主题、任务等全家桶 | **正式采用** |
| Gin | 生态大、教程多、API 开发快、性能好 | 自有 Context 抽象更强，迁移到纯标准库成本略高 | 备选，不进入当前核心 |
| Echo | 路由、中间件、绑定和验证比较完整 | 框架 API 面积比 Chi 大 | 备选 |
| Fiber | 基于 `fasthttp`，微基准表现高，API 类似 Express | 与标准 `net/http` 中间件不完全兼容，真实 CMS 瓶颈通常不在路由 | 不采用 |
| Hertz | 高性能、代码生成与微服务能力强 | 复杂度高，第一版单体 CMS 用不上 | 不采用 |
| GoFrame | 中文生态和全栈能力完整 | 组件面较重，不符合当前轻量目标 | 不采用 |
| Beego | 传统 MVC 能力完整 | 现代新项目的轻量性和组合自由度不足 | 不采用 |
| Kratos / Goa | 适合微服务、RPC、接口契约 | 不适合第一版单体内容系统 | 不采用 |

选择 Chi 的核心原因不是追求微基准第一，而是用很小的抽象获得路由、中间件和模块组织，同时保留 Go 标准库的兼容性、安全更新与测试工具。

## 3. 为什么 Go 适合本项目

- 编译为单一二进制，部署和回滚简单；
- 空闲内存和并发连接成本可控；
- 标准库 HTTP、模板、加密、JSON、测试与性能分析工具完整；
- Goroutine 适合页面生成、图片处理、批量本土化和发布任务；
- 原生支持优雅停止、请求超时、Context 取消和竞争检测；
- 服务端模板可以直接输出 Google 可抓取的完整 HTML；
- 不需要常驻 Node.js SSR 进程，也不需要 PHP-FPM/FrankenPHP Worker。

Go 不能自动保证高性能。慢 SQL、无索引列表、过大的模板数据、无限 Goroutine、缓存错误和频繁磁盘同步仍会让系统变慢，因此必须通过压测和可观测数据验收。

## 4. 原生 HTML 与 SEO 输出

### 4.1 前台渲染

- 使用 Go `html/template` 服务端渲染；
- 响应正文直接包含标题、正文、导航和内链，不依赖 JavaScript 二次抓取；
- 每个 `Site + Market + Locale + Page` 独立输出 SEO Title、Meta Description、Canonical、robots、Open Graph 和 JSON-LD；
- `hreflang` 只输出真实存在、已发布、可索引且语义对应的页面；
- Sitemap 和 robots.txt 由 Go 发布模块生成；
- 高频公开页面可生成静态 HTML 并交给 CDN 或 Nginx/Caddy 直接返回。

### 4.2 后台渲染

- 中文后台同样由服务端模板输出原生 HTML；
- CSS 使用项目设计令牌和可复用组件类；
- JavaScript 使用 ES Modules，对搜索、弹窗、筛选、批量选择等功能做渐进增强；
- 核心表单必须能通过标准 HTTP 提交，不能把数据保存能力只放在前端内存中；
- 后台响应统一输出 `X-Robots-Tag: noindex, nofollow`。

### 4.3 模板安全

- 使用 `html/template` 的上下文自动转义；
- 富文本进入模板前经过服务端 HTML 白名单清洗；
- 自定义模板只允许登记过的模板函数；
- 模板包不能载入 Go 插件、执行 SQL、执行系统命令或读取白名单外文件；
- 生产模板发布前进行语法、链接、SEO、可访问性、响应式和性能检查。

## 5. SQLite 选型与边界

### 5.1 适合当前阶段的原因

- CMS 是自用后台，写入用户有限；
- 公开流量主要读取静态 HTML 或缓存，不直接放大数据库并发；
- SQLite 无独立数据库服务，部署、备份、恢复和迁移成本低；
- 读取性能强，事务和外键完整；
- 单文件便于早期运维，但备份必须使用 SQLite 在线备份接口或安全快照，不能只复制正在写入的主文件。

### 5.2 强制参数

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA temp_store = MEMORY;
PRAGMA cache_size = -20000;
PRAGMA mmap_size = 268435456;
```

实际值必须通过目标服务器压测确定，不能盲目增加 mmap 或缓存占用。

### 5.3 写并发规则

SQLite 在任一时刻只允许一个写事务。本项目必须：

- 写事务尽量短小；
- 不在事务中调用 AI、HTTP、Redis、对象存储或图片处理；
- 大批量任务分批提交，每批数量通过压测确定；
- 后台异步写入使用有界队列，禁止无限创建 Goroutine；
- 对锁等待、写延迟、WAL 大小和检查点耗时告警；
- 所有写接口具备幂等键或冲突处理；
- 长时间读取采用游标分页，不长期占用读事务阻塞 WAL 回收。

### 5.4 数据量边界

SQLite 文件可存储很大数据，但“能存入”不代表“业务性能合格”。必须分别压测：

- 100 万与 1,000 万内容元数据；
- 六种以上 Locale 的内容读取；
- 50 个并发后台读取与持续发布写入；
- FTS5 搜索、游标分页、版本回滚；
- 在线备份、恢复和 WAL 检查点；
- 数据库文件达到 10GB、50GB 等阶段时的恢复时间。

出现以下情况时触发迁移评估：

- P95 写锁等待持续超过约定阈值；
- 持续写入吞吐无法满足发布任务；
- 单库备份或恢复窗口不可接受；
- 需要多台应用跨区域同时写入；
- 复杂分析查询影响在线业务；
- FTS5 无法满足目标语言的分词、聚合或排序质量。

业务层通过 Repository 接口访问数据，达到阈值后可迁移 PostgreSQL 或独立搜索服务。

## 6. 内存、Redis 与 SQLite 的职责

| 层级 | 职责 | 是否可丢失 | 是否强依赖 |
|---|---|---|---|
| Go 进程内存 L1 | 站点配置、路由、语言、模板绑定和热点查询 | 可以，重启后重建 | 是，但属于进程自身 |
| Redis L2 | 多实例共享缓存、会话、限流、锁、任务状态、失效通知 | 缓存可丢失；会话按策略处理 | 否，故障时降级 |
| SQLite | 所有业务主数据、版本、权限、SEO、任务与审计 | 不可丢失 | 是 |
| 静态 HTML / CDN | 已发布公开页面和资源 | 可由 SQLite 重建 | 公开访问优先层 |

### 6.1 读取流程

```text
请求
→ 查询进程内存 L1
→ 未命中则查询 Redis L2（如已启用）
→ 未命中则查询 SQLite
→ 回填 Redis 与内存
→ 返回结果
```

### 6.2 写入与失效流程

```text
验证权限和输入
→ 开启 SQLite 短事务
→ 写入主数据、版本和 Outbox/任务记录
→ 提交 SQLite
→ 删除本机内存缓存
→ 删除 Redis 缓存并发布失效消息
→ 触发静态页面增量生成
```

不得在 SQLite 提交前先更新缓存。缓存失效失败时记录 Outbox 重试，不能回滚已经正确提交的业务数据。

### 6.3 Redis 降级

- `CZCMS_REDIS_ADDR` 未配置时，只使用内存和 SQLite；
- Redis 启动检查失败时记录告警并继续启动；
- 单次 Redis 超时严格限制，不能拖慢页面主链路；
- Redis 恢复后逐步回填，不执行阻塞全站的同步预热；
- 认证、限流等安全功能在 Redis 故障时采用明确的本机降级规则，不得默认全部放行。

## 7. SQLite 驱动选择

### 第一版：`modernc.org/sqlite`

- 纯 Go 实现，不依赖 CGO；
- 交叉编译和容器部署简单；
- 适合单一二进制目标；
- 必须通过真实数据压测确认写入、FTS5、备份和内存占用。

### 备选：`github.com/mattn/go-sqlite3`

- 生态成熟，调用原生 SQLite；
- 通常具有很好的实际性能；
- 需要 CGO 和对应构建工具链，交叉编译与静态链接更复杂。

Repository 层只依赖 `database/sql`，驱动切换不得修改业务服务。

## 8. 模块化单体结构

建议目录：

```text
cmd/czcms/                 程序入口
internal/app/              应用装配
internal/config/           环境配置
internal/httpserver/       Chi 路由、中间件和 Handler
internal/database/         SQLite 连接与迁移
internal/cache/            内存与 Redis 分层缓存
internal/site/             站点与国家市场
internal/localization/     语言与 AI 本土化
internal/content/          内容、版本和审核
internal/theme/            模板与绑定
internal/seo/              SEO、Sitemap 与 hreflang
internal/publishing/       静态发布和缓存失效
internal/jobs/             持久化任务与 Worker Pool
web/templates/             Go HTML 模板
web/static/                CSS、JavaScript、SVG 与图片
```

模块通过服务接口协作，禁止 Handler 直接拼接跨模块 SQL。Go `internal` 目录用于限制外部包依赖。

## 9. 异步任务方案

第一版不强制 RabbitMQ：

- SQLite `jobs` 表持久化任务；
- Worker 通过短事务领取任务并写入租约截止时间；
- 每个任务具有幂等键、优先级、尝试次数、下次重试时间和死信状态；
- Worker Pool 设定并发上限和每类任务限额；
- 应用停止时不再领取新任务，等待当前任务完成或安全归还租约；
- AI、媒体和批量发布分别配置超时、并发和资源预算。

需要多实例高吞吐消费时，可增加 Redis Streams。是否引入专用消息队列必须由积压、吞吐和可靠性数据决定。

## 10. 搜索方案

第一阶段使用 SQLite FTS5：

- 内容标题、摘要、正文和关键词分离索引；
- 英语等语言使用适合的 Tokenizer；
- 德语、法语、西班牙语、意大利语和荷兰语需要测试重音、词形和停用词；
- 中文或无空格语言不能直接假设默认 Tokenizer 质量足够；
- 索引更新与内容版本使用事务或持久化任务保持一致；
- 搜索输入限制长度、超时和通配符复杂度。

如果需要复杂多语言词干、同义词、聚合或高亮质量，再通过 Search Repository 接入 Meilisearch、Typesense 或 OpenSearch；第一版不强制部署。

## 11. 安全基线

- Go 版本和依赖进入自动漏洞扫描；
- 后台认证使用安全 Cookie、CSRF、防会话固定、MFA 和速率限制；
- 密码使用 Argon2id，并保存可升级的算法参数；
- 所有 SQL 使用参数绑定，动态排序字段使用白名单；
- `html/template` 自动转义，富文本额外白名单清洗；
- 上传内容按真实文件签名验证，并与 Web 根目录隔离；
- 管理后台输出 CSP、`X-Content-Type-Options`、`frame-ancestors` 和 Referrer Policy；
- 日志不记录密码、Token、Cookie、AI 密钥和询盘敏感正文；
- SQLite 文件、WAL、备份和密钥目录使用最小文件权限；
- 高风险操作需要二次确认、权限校验和不可抵赖审计记录。

## 12. 性能策略

按优先级实施：

1. 公开页面静态 HTML + CDN；
2. 正确 SQLite 索引、游标分页和只取所需字段；
3. 进程内存 L1；
4. 可选 Redis L2；
5. 页面和模板片段缓存；
6. 有界 Worker Pool 把 AI、图片和发布移出请求；
7. `pprof`、执行计划、慢查询和真实压测驱动优化。

禁止用无限 Goroutine、无限连接池、无限缓存或扩大服务器配置掩盖设计问题。

建议应用层初始参数：

- HTTP Header 读取超时 5 秒；
- 普通读取请求超时 15 秒；
- 响应写入超时 30 秒；
- 空闲连接超时 60 秒；
- 请求头限制 1MB；
- SQLite 连接池从 4–8 个连接压测起步；
- 写 Worker 初始为 1，读取和 CPU 任务另设有界并发。

## 13. 服务器规格建议

### 开发/测试

- 2 核 CPU；
- 2GB 内存可运行，4GB 更舒适；
- SSD；
- Go 应用 + SQLite；
- Redis 可不启用。

### 第一阶段生产

- 2–4 核 CPU；
- 4–8GB 内存；
- NVMe SSD；
- Go 应用、SQLite、进程内存缓存；
- Redis 可同机或托管；
- 媒体较多时使用对象存储；
- CDN 服务公开静态页面。

### 扩容顺序

1. 先确认静态化、缓存命中和 SQL 索引；
2. 增加 Redis 共享缓存；
3. 把媒体迁移对象存储；
4. 将 AI/图片/发布 Worker 独立进程化；
5. 按站点归档或拆分 SQLite；
6. 达到写并发边界后迁移 PostgreSQL；
7. 达到搜索质量/容量边界后增加独立搜索服务。

- `go test ./...`：单元与集成测试；
- `go test -race ./...`：数据竞争测试；
- `go vet ./...`：基础静态分析；
- `staticcheck`：更严格的 Go 静态检查；
- `govulncheck ./...`：依赖漏洞扫描；

- `go test -bench`：缓存、模板和 SQLite 基准；
- 浏览器回归：桌面、平板、手机、键盘和减少动态效果；
- `EXPLAIN QUERY PLAN`：关键 SQLite 查询计划验收；
- 备份恢复演练：不以“生成了备份文件”代替实际恢复成功。

## 15. 开发阶段

### 阶段一：轻量工程骨架

- Go 程序入口、配置和优雅停止；
- Chi 路由、安全响应头和访问日志；
- SQLite WAL、迁移和种子数据；
- 内存缓存、可选 Redis 和健康检查；
- 原生 HTML 中文后台控制台。

### 阶段二：CMS 核心

- 用户、MFA、RBAC 和审计；
- 站点、语言、国家市场和内容模型；
- 内容版本、审核、回收站和媒体；
- 模板套装与每语言独立绑定。

### 阶段三：SEO 与发布

- 伪静态、Canonical、hreflang、Sitemap、robots 和 JSON-LD；
- 静态生成、原子切换、缓存失效和回滚；
- AI 语境本土化、字段锁定和人工审核；
- FTS5 搜索与关键词规划。

### 阶段四：大数据验证

- 100 万/1,000 万记录压测；
- 写锁、WAL、备份恢复和磁盘容量验证；
- Redis 降级与多实例缓存失效；
- 根据真实阈值决定是否迁移 PostgreSQL 或独立搜索服务。

## 16. 第一阶段验收

- Go 应用可由一个命令构建并生成单一可执行文件；
- Redis 未配置或故障时应用仍可启动并完成核心读写；
- SQLite 参数、迁移、外键和 WAL 生效；
- 后台页面由服务端返回完整原生 HTML，并输出 `noindex`；
- 公开页面在禁用 JavaScript时仍有正文与完整 SEO 元素；
- 缓存读取和写后失效顺序通过自动化测试；
- HTTP 超时、安全响应头、CSRF、认证和限流通过测试；
- Go 单元测试、竞争检测、静态检查和漏洞检查通过；
- 关键页面在约定服务器与数据规模下达到性能目标；
- 数据库与媒体备份完成实际恢复演练。

## 17. 当前已建立的工程基线

当前仓库已经包含：

- Go 程序入口和优雅停止；
- Chi 路由与安全响应头；
- SQLite WAL、基础 Schema 和六种首批语言种子；
- L1 内存缓存、可选 Redis L2 与降级逻辑；
- 嵌入式原生 HTML 后台资源；
- Argon2id 登录、安全 Cookie 会话、CSRF、登录限流、账户锁定与 TOTP MFA；
- RBAC、站点/语言数据范围、用户安全 API 和追加式审计日志；
- 富文本白名单、媒体真实类型校验、声明式模板包验证与生产防病毒门禁；
- TLS 启动、Redis ACL/TLS 校验、AES-256-GCM 加密备份和离线恢复校验；
- `govulncheck`、竞态检测 CI、安全回归测试和系统健康 API。
- `internal/catalog` 业务层、正式版本迁移、站点与动态语言 CRUD、多语言内容组、Locale 独立 SEO、乐观锁和修订快照；
- 中文后台已将站点、语言、内容与 SEO 三个核心模块接入真实安全 API，其余模块仍按后续阶段逐步实现。

后续业务模块必须沿用本方案，不得在 Handler 内直接写跨模块 SQL，也不得把 Redis 或内存缓存变成业务真相来源。

详细配置、接口安全边界、备份恢复和验证方式见：[安全实现与运维手册](./security-operations.md)。
